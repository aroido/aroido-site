VibeSmith

AI 코딩 레포 드리프트를 번지기 전에 진단하세요.

VibeSmith는 멀티 레포 팀이 Cursor·Claude Code 워크플로우 전반에서 활성 컴포넌트, 종속성 리스크, 컨텍스트가 무거운 재사용 패턴을 한 곳에서 검토할 수 있게 합니다. 지금 GitHub 오픈소스로 공개되어 있으며 무료로 설치할 수 있습니다.

세 번째 레포부터 킥오프 품질이 떨어진다면 여기서 시작하세요.

첫 화면

대시보드 한 화면으로 무엇부터 검토할지 바로 파악하세요

첫 화면에서 활성 컴포넌트 규모, 프로젝트 범위, 초기 충돌 신호를 기준선으로 보여주기 때문에 무엇을 복사하고 정리하고 표준화할지 먼저 결정할 수 있습니다.

  • skills, rules, commands, hooks 전반의 운영 기준선
  • 재사용이 퍼지기 전에 보는 충돌·종속성 신호
  • 다음 킥오프 전에 정리 대상을 잡는 프로젝트별 분해

현재 공개 오픈소스 빌드의 대시보드 화면입니다.

먼저 보이는 것

팀이 대개 너무 늦게 발견하는 문제를 먼저 보세요

VibeSmith는 여러 레포에 걸친 세팅 드리프트, 재사용 리스크, 컨텍스트가 무거운 스프롤을 한 레이어에서 보이게 할 때 가장 유용합니다.

드리프트

컨텍스트가 무거운 세팅

새 프로젝트가 같은 스프롤을 물려받기 전에 어떤 레포 레이어가 메모리, 지시문, 세팅 노이즈를 과하게 떠안고 있는지 먼저 확인합니다.

재사용

숨은 재사용 리스크

컴포넌트와 함께 무엇이 같이 움직여야 하는지 검토해, 복붙 부트스트랩이 부분적으로만 성공하는 상황을 줄입니다.

릴리즈

종속성과 충돌 깜짝 이슈

연결된 리스크를 더 이른 시점에 드러내어 릴리즈 주간 리뷰가 첫 발견 지점이 되지 않게 합니다.

첫 진단에서 필요한 것

팀이 첫 실사용 진단에서 보고 싶어 하는 것

반복되는 요구는 또 다른 AI 기능이 아니라 여러 레포를 가로지르는 더 선명한 운영 시야입니다.

니즈 01

실제로 활성인 기준을 알고 싶다

비슷해 보이지만 동작은 다른 룰, 명령, 가이드가 레포마다 섞이면 팀은 금방 시간을 잃습니다.

니즈 02

연결된 맥락을 잃지 않고 재사용하고 싶다

팀은 반쯤 작동하는 조각이 아니라, 종속성까지 포함된 안전한 기준선을 가져가고 싶어 합니다.

니즈 03

컨텍스트 낭비가 리뷰 낭비로 커지기 전에 줄이고 싶다

섞인 메모리 레이어와 오래된 자산은 토큰 낭비, 시끄러운 프롬프트, 긴 리뷰 루프를 만듭니다.

핵심 워크플로우

VibeSmith가 드리프트를 줄이는 방식

활성 기준선을 찾기

통합 인벤토리와 검색으로 프로젝트 전반에서 어떤 Skills, Agents, Commands, Hooks, Rules가 실제로 활성인지 확인합니다.

연결 조각을 놓치지 않고 재사용

종속성을 함께 검토하며 복사해 부트스트랩이 중간에 깨지지 않도록 만듭니다.

쓰기 전에 롤아웃 영향을 검토

충돌 정책과 함께 미리보기/적용을 거쳐 공유 세팅 변경의 영향 범위를 먼저 판단할 수 있습니다.

릴리즈 주간 전에 리스크 보기

종속성 그래프, 충돌 리뷰, 프로젝트 범위 뷰로 숨은 결합을 더 빨리 찾아냅니다.

왜 지금

AI 코딩 툴은 한 레포를 빨리 만들지만, 여러 레포를 설명해주진 않습니다

Cursor, Claude Code, MCP는 강한 로컬 도구입니다. 팀이 여러 레포에 같은 운영 명확성을 유지해야 할 때 시스템 갭이 드러납니다.

Cursor의 세션 단위 컨텍스트는 팀이 채팅 기억 대신 재사용 기준을 바깥 레이어로 꺼내게 만듭니다.

Claude Code의 다중 스코프 메모리/설정은 공유 운영 레이어가 없으면 정합성 비용을 키웁니다.

MCP 확장 시 서버 스코프와 권한 경계를 사전 검토하는 운영 규율이 필수입니다.

첫 주 지표

첫 주에 실제로 봐야 할 것

제품 가치가 있는지는 거대한 롤아웃이 아니라 레포 하나의 기준선이 더 명확해졌는지로 먼저 판단할 수 있습니다.

결과 01

더 빠른 첫 안정 세팅

설치부터 팀이 유지하고 싶은 기준선에 도달하기까지 걸리는 시간.

결과 02

레포 간 깜짝 이슈 감소

첫 재사용 이후에도 복사한 룰, 명령, 컴포넌트가 얼마나 일관되게 남는지.

결과 03

더 선명한 정리 대상

컨텍스트 품질이 무너지기 전에 무엇을 지우고, 정리하고, 분리해야 하는지.

도입 경로

레포 하나로 먼저 증명하세요

전사 마이그레이션은 필요 없습니다. 작게 시작해 드리프트를 측정하고, 기준선이 개선될 때만 확장하세요.

1단계

실사용 레포 하나 연결

같은 세팅 질문이 반복되는 레포에 오픈소스 빌드를 설치하고 먼저 스캔합니다.

  • 산출물: 활성 컴포넌트와 드리프트 지점의 첫 기준선
  • 산출물: 설치 마찰 노트

2단계

재사용과 종속성 리스크 검토

인벤토리, 상세, 종속성 뷰로 기억에 의존한 세팅 복사에서 어디가 깨지는지 확인합니다.

  • 산출물: 정리 후보 목록
  • 산출물: 연결된 종속성 리스크

3단계

워크플로우 하나가 더 명확해진 뒤 확장

한 팀이 세팅을 더 명확히 설명할 수 있게 된 뒤에만 다른 레포 확장을 결정합니다.

  • 산출물: 유지 / 수정 / 확장 결정
  • 산출물: 더 깊은 협업 또는 Pro 검토 목록

도입 경계

설정 드리프트가 이미 딜리버리 속도를 늦추고 있다면 효과가 큽니다.

명확한 경계가 있어야 멀티 레포 팀이 과투입 없이 빠르게 판단할 수 있습니다.

적합한 경우

  • 활성 레포 3개 이상이 하나의 릴리즈 일정으로 묶여 있을 때
  • 규칙 전달이 수동이라 킥오프 품질이 흔들릴 때
  • 릴리즈 리뷰에서 종속성 이슈가 반복적으로 늦게 발견될 때

아직 이른 경우

  • 단일 레포 중심이고 세팅 기준 변경이 거의 없는 경우
  • 컴포넌트 리뷰 기준을 명확히 정의하기 어려운 워크플로우
  • 롤아웃 설계 없이 즉시 완전 자동화를 기대하는 워크플로우

현재 단계의 의도적 범위

현재 범위를 좁게 두는 건 의도적입니다. 더 넓은 자동화 약속보다 눈에 보이는 증거를 먼저 만듭니다.

  • 레포 구조를 강제로 바꾸지 않습니다. 기존 구조를 먼저 맵핑합니다.
  • 클라우드 전역 정책 자동화는 후속 단계이며 1단계 필수 조건이 아닙니다.
  • 공유 롤아웃 레이어는 실제 레포 진단에서 반복 근거가 쌓인 뒤에만 확장합니다.

옵션 B. Homebrew 가이드

GitHub Homebrew tap이 같은 공개 릴리즈 채널을 추적합니다. Homebrew로 바로 설치하고, 예전 GitLab 경로를 썼다면 먼저 retap 하세요.

설치 및 업그레이드

brew update
brew tap aroido/vibesmith https://github.com/aroido/homebrew-vibesmith.git
brew install --cask aroido/vibesmith/vibesmith

# 이미 구버전이 설치되어 있다면:
brew update
brew upgrade --cask --greedy aroido/vibesmith/vibesmith

Homebrew 설치와 업그레이드는 이 경로를 우선 사용하세요. 레거시 GitLab tap을 썼다면 `brew untap aroido/vibesmith` 후 다시 tap 하세요.
